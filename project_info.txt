================================================================================
PONYO - CLASH OF CLANS CLAN DATA SYNC + DISCORD AI BOT
Developer Reference
================================================================================

WHAT THIS IS
------------
1. SYNC: pulls data from the official CoC API on a schedule into a Supabase
   (PostgreSQL) database using a human-readable UID system
   (CW001, CWL001-D1-ATK01, CR001-R1-ATK001).
2. ANSWER: two Discord slash commands -- /ask (Sarvam LLM, fast) and
   /tell (Gemini LLM, deeper) -- answer natural-language questions about
   the clan. A deterministic query layer fetches structured rows (Supabase
   + live CoC API), embeds them into the LLM context as the authoritative
   source, and the LLM only polishes wording.

Entry points: npm start -> src/runtime.js (Discord bot), npm run sync ->
src/index.js (sync scheduler). One Render web service runs the bot.

ANSWER PIPELINE (READ THIS FIRST)
---------------------------------
1. discord.js handleAiCommand() loads the last 5 turns (ai_conversations,
   in-RAM fallback) and builds TWO strings: question (the CURRENT
   question only) and contextualQuestion (question + conversation
   history). It calls generator(question, contextualQuestion).
2. ai.js answerWithAi() calls buildContext(question) with ONLY the
   current question -- history must never enter scope detection, or old
   turns mentioning e.g. "capital raid" hijack the routing of a new
   "clan war" question (real bug, see git history).
   runDeterministicQuery(question) produces structured_query, which the
   system prompt declares AUTHORITATIVE for filters/counts/rankings.
3. provider(contextualQuestion, context) -- askSarvam or askGemini.
   History is used ONLY to resolve follow-ups (they/them/that war).
4. On provider failure: falls back to deterministic text with a note.
5. discord.js splits the reply into 1800-char pages (max 10 list items
   per page); the full answer is stored in ai_answers for See more/less.

QUERY UNDERSTANDING (src/queryEngine.js, pure and unit-tested)
---------------------------------------------------------------
buildQueryPlan(question) returns scope (checked in order cwl -> capital ->
war -> clan -> general; negated mentions like "not capital raid" are
stripped first via stripNegatedDatasets()), an operation (clan_identity,
member_attack_usage, opponent, state, timing, statistics, members,
member_metric, role_members) and filters (unused = 0 attacks,
attacks_used exact, attacks_used_min for "at least N", attacks_remaining
for "N attacks left"). applyAttackUsageFilters() is the ONE shared filter
implementation for both the pure executor and the DB-backed router
(src/queryRouter.js), so their results never diverge.

ROUTING (src/queryRouter.js): war questions prefer the LIVE CoC API
(state, time left, fresh members/attacks) with the Supabase cw_session as
fallback; cwl is scoped to the latest synced league day; capital to the
latest synced season. For plan.unused capital questions the answer comes
from the season ABSENTEES list, not participant rows (see below).
LIVE DATA (src/liveData.js): getLiveWar/getLiveCapital call the CoC API
at answer time, cached 45 s (LIVE_DATA_TTL_MS); failed fetches re-serve
the last known value for 10 s.


================================================================================
SUPABASE -- DEEP DIVE
================================================================================

PROJECT
-------
One Supabase project (PostgreSQL 17), everything in the public schema.
Canonical DDL is supabase/ponyo_schema.sql; incremental fixes are dated,
idempotent files in supabase/migrations/.

TWO SEPARATE CLIENTS (security-relevant)
----------------------------------------
  src/db.js         SUPABASE_URL + SUPABASE_SERVICE_ROLE_KEY
                    Service-role client, used ONLY by the sync layer.
  src/retrieval.js  SUPABASE_URL + SUPABASE_ANON_KEY (or _READONLY_KEY)
                    Read-only client used by the AI answer path.
db.js also exports upsert(table, rows), which resolves the correct
onConflict key per table from a hardcoded map (conflictKeys).

ROW LEVEL SECURITY
-------------------
RLS is ENABLED on every table. The schema creates per-table SELECT
policies (pony_read_<table>) allowing anonymous reads for the answer path.
Writes are only possible with the service-role key. There are deliberately
no INSERT/UPDATE/DELETE policies for anon.


THE UID SYSTEM
--------------
Every event row carries a human-readable sequential UID, allocated as
MAX(existing)+1 per table via uidAlloc.allocateSeq:

  CW001                 one normal clan war session
  CW001-ATK001          one attack inside that war
  CWL001                one CWL season
  CWL001-D1             one league day (battle) inside the season
  CWL001-D1-ATK01       one attack inside a league day
  CR001                 one Capital Raid weekend (a season)
  CR001-R1              one raid (one attacked defender clan) inside the
                        weekend; R-numbering is stable across re-syncs
                        (assigned in API order per defender)
  CR001-R1-ATK001      one attack inside that raid

CRITICAL RULE -- how re-syncs resolve an existing event (uidAlloc.js):
findWarSessionUid and findCapitalSeasonUid compare timestamps BY INSTANT
(new Date(a).getTime() === new Date(b).getTime()), NEVER by string equality.
PostgREST returns timestamptz as 2026-09-18T07:00:00+00:00 while the CoC API
path produces 2026-09-18T07:00:00.000Z. String comparison never matches,
which historically made every sync allocate a NEW UID for the same
war/weekend, duplicating each event ~10x (fixed by
migrations/20260919b_dedupe_event_copies.sql). Keep the instant comparison.
CWL lookups match on stable identifiers instead of timestamps: seasons by
data->>season, days by data->>warTag.


TABLES
------
Sync domain (service-role writes; every table has a data jsonb column
with the raw API payload for debugging/re-derivation):

  clan_info                 Current roster, one row per player, player_id
                            (= CoC #TAG) primary key. Roles are RAW CoC
                            values: leader, coLeader, admin, member.
                            admin means ELDER in-game, never display it
                            as a Discord admin. last_active = snapshot
                            diffs.
  clan_info_snap            Periodic roster snapshots (one batch per
                            date_time). Used for activity detection and to
                            reconstruct the roster when a capital weekend
                            began. Trimmed to the last 12 batches.
  cw_session                One normal war. Unique cw_uid. Identified by
                            its battle window; warlog imports have NULL
                            battle_start and only battle_end.
  cw_session_participants   One row per war roster player. Unique (cw_uid,
                            player_id). attacks_available=2.
  cw_attacklog              One row per attack; delete+inserted per war.
  cwl_seasons               One CWL season, unique generated_cwl_id.
  cwl_daywise_attacklog     One row per league day; carries both
                            participant lists as jsonb; resolves by
                            data->>warTag.
  cwl_season_participants   One row per player per league day. Unique
                            (cwl_day_uid, player_id). attacks_available=1.
  cwl_attacklog             Attacks per league day, delete+inserted.
  capital_raid_season       One raid weekend. Unique generated_uid. Stores
                            participants_name / absentees_name arrays and
                            participants_no / absentees_no (see below).
  capital_raid_participants One row per member PER WEEKEND who has
                            attacked at least once. Unique
                            (capital_raid_uid, player_id).
                            attacks_available = attackLimit +
                            bonusAttackLimit (so 6 on bonus weekends).
  capital_raid_attacklog    One row per attack, delete+inserted per season;
                            raid_no is the R-number of the defender clan.
  sync_runs                 Health log per sync job execution (job, status
                            ok/error, details jsonb, message). Check this
                            FIRST when a sync looks wrong.

AI domain (via aiState.js):
  ai_chat             Raw question/answer log.
  ai_conversations    Per user+guild+channel rolling memory for follow-ups;
                      expiry-based cleanup.
  ai_answers          Stored full answers backing the See more/See less
                      buttons; expiry + Discord message id attachment.

WRITE PATTERNS -- three rules, do not break them:
  1. Attack tables (cw_attacklog, cwl_attacklog, capital_raid_attacklog)
     and ALL participant tables are DELETE+INSERTED per event on every
     sync. This makes re-syncs idempotent even where a unique constraint
     is missing, so duplicate players can never accumulate.
  2. Session/season/day headers are upserted with onConflict on their UID.
  3. clan_info is upserted on player_id; snapshots are plain inserts.


CAPITAL RAIDS -- THE ABSENTEE RULE (very important)
---------------------------------------------------
The CoC API capitalraidseasons endpoint returns members ONLY for players
who have already attacked at least once in the weekend. A player with 0
attacks is simply NOT in that array. Consequences:
  - capital_raid_participants can never answer who-has-not-attacked.
  - The sync computes absentees = (clan roster snapshot at weekend start)
    minus (attackers) and stores them on the season row
    (transform.js participantStats).
  - queryRouter answers plan.unused capital questions from
    season.absentees, and ai.js exposes capital_current_season.absentees
    to the LLM so it cannot improvise the list from war data.
If you change how participants are stored, preserve this computation or
who-has-not-attacked-in-the-capital-raid silently breaks.


DATA NORMALIZATION CONVENTIONS
-------------------------------
  - CoC role values stored raw (leader, coLeader, admin, member); warlog
    results win/lose/tie normalized to win/loss/draw.
  - Timestamps are timestamptz instants; the display layer converts to
    IST (DD/MM/YYYY HH:mm, Asia/Kolkata).
  - Player identity = CoC player tag (#XXXX) as player_id / attacker_id /
    defenderTag depending on table.

MIGRATIONS
----------
  supabase/ponyo_schema.sql                         full canonical schema
  supabase/migrations/20260919_dedupe_participants.sql
       duplicate participant cleanup + unique (event, player) constraints
  supabase/migrations/20260919b_dedupe_event_copies.sql
       collapses duplicated war/season headers (one per battle window,
       newest UID kept) and deletes their stale child rows.
Run migrations in the Supabase SQL editor; they are idempotent. Schema
changes go into NEW dated migration files, never edit old ones.


================================================================================
SYNC SCHEDULER, DISCORD, ENVIRONMENT
================================================================================

Scheduler (src/index.js), defaults all env-configurable: clan 10 min
(roster upsert), war 1 min, history 3 min (warlog), capital 1 min, cwl
1 min, player-snapshot 3 min. Toggles: ENABLE_CLAN/WAR/HISTORY/CAPITAL/
CWL/PLAYER_SNAPSHOT_SYNC (default true), STARTUP_* variants for the boot
run, ENABLE_SYNC_SCHEDULER to disable everything. A single-flight guard
prevents overlapping runs. On boot, migrateLegacyUids converts
timestamp-based legacy IDs to the CW/CWL/CR scheme once, before any sync
writes. Warlog history rows contain summaries only -- attack rows for
past wars exist only for wars captured live via currentwar.

Discord (src/discord.js): replies are EPHEMERAL (private to the asking
user; Discord does not allow pinning or forwarding ephemeral messages --
a platform limitation, not a bug). Provider failures are classified
(context window / credits / rate limit / auth / temporary) into friendly
messages; a detailed alert goes to PONYO_ALERT_CHANNEL_ID when set.

ENVIRONMENT VARIABLES
----------------------
  SUPABASE_URL / SUPABASE_SERVICE_ROLE_KEY     sync writes
  SUPABASE_ANON_KEY (or _READONLY_KEY)         answer-path reads
  COC_API_TOKEN / COC_CLAN_TAG                  CoC API
  DISCORD_TOKEN / DISCORD_CLIENT_ID
  DISCORD_GUILD_ID                 optional; scopes commands to one guild
  DISCORD_CLEANUP_GUILD_COMMANDS   'true' clears stale guild commands
  PONYO_ALERT_CHANNEL_ID           optional provider-error alert channel
  SARVAM_API_KEY / SARVAM_MODEL    /ask (default sarvam-105b)
  GEMINI_API_KEY / GEMINI_MODEL    /tell (default gemini-3.8-flash)
  LIVE_DATA_TTL_MS                live-data cache TTL (default 45000)
  SNAPSHOT_KEEP_BATCHES           roster snapshot batches to keep (12)
  ENABLE_*_SYNC / STARTUP_*_SYNC / ENABLE_SYNC_SCHEDULER  (see scheduler)

TESTS, CI, DEPLOYMENT
---------------------
npm test runs 32 unit tests: queryEngine (routing, filters, negation,
role mapping), uids, sync transforms, liveData normalizers. CI runs on
every push. cocApi.js throws at import time without COC_API_TOKEN --
tests that import it set a dummy token before a dynamic import. Deploy:
single Render web service (npm start); enable auto-deploy or it silently
runs stale code. npm run sync can be run manually against a .env.

KNOWN GOTCHAS (read before touching anything)
---------------------------------------------
  1. Timestamp comparisons: by instant, never string equality.
  2. Capital participants only include attackers; absentees live on the
     season row.
  3. Scope detection must only ever see the CURRENT question. History
     goes to the LLM prompt, not the router.
  4. Role admin = in-game Elder; coLeader is camelCase in the data.
  5. Participants/attacks are delete+inserted; headers upserted by UID.
  6. 6-attack capital weekends (attackLimit + bonusAttackLimit) are
     correct CoC data, not a bug.
  7. The database/ folder is design notes and is never written by the bot.
